Loading 100 million rows into Postgres on a laptop

Part of Chapi's 100M Row Challenge • Thanks to @Robi_makes_stuff • PostgreSQL 18.1 + Go 1.26

When you build CRUD apps with 10,000 or even 100,000 rows, databases are polite. PostgreSQL will forgive missing indexes, forgive unoptimized queries, and quietly cache everything in RAM.

Once you cross 20, 50, and 100 million rows, the database stops being polite and starts teaching you physics: memory limits, disk I/O bottlenecks, cache thrashing, WAL pressure, and table bloat.

This is what happened when I ingested, broke, tuned, and benchmarked 100,000,000 physical rows on a standard consumer laptop.

The setup: can my laptop survive 100 million rows?

Before attempting this, I had an honest question: will consumer hardware freeze, thrash the NVMe drive to death, or run out of disk space?

CPU: 12th Gen Intel Core i5-1240P (12 cores, 16 threads, up to 4.4 GHz)
RAM: 16 GB DDR4/DDR5
Disk: NVMe SSD (~149 GB free space)
Database: Native PostgreSQL 18.1 (Windows Service)
Loader: Native Go 1.26 with pgx/v5 binary connection pool

For the database, I went with a Hacker News-like schema with these fields: 

CREATE TABLE hn_items (
    id BIGSERIAL PRIMARY KEY,
    parent_id BIGINT,
    created_at TIMESTAMPTZ NOT NULL,
    score INT NOT NULL DEFAULT 0,
    deleted BOOLEAN NOT NULL DEFAULT FALSE,
    deleted_at TIMESTAMPTZ DEFAULT NULL,
    item_type VARCHAR(16) NOT NULL,
    author VARCHAR(32) NOT NULL
);

Each row on disk averages around 76.8 bytes with tuple headers. Across 100 million rows, the raw table heap sits at roughly 7.68 Gigabytes.

Why I didn't include text in the schema

Leaving out a text or body column might seem counterintuitive for a Hacker News dataset, but it comes down to three practical reasons: storage math, PostgreSQL TOAST behavior, and how production systems actually work.

1. Storage math on 100 million rows. Hacker News comments average between 250 and 500 bytes of raw text. If you multiply that across 100 million rows:

100,000,000 rows × 350 bytes ≈ 35 Gigabytes of raw text alone.

Once you account for Postgres row headers, alignment padding, and B-Tree indexes, a single table would balloon past 75 GB. On a 512GB laptop SSD shared with the operating system and dev tools, that eats up available space fast without adding anything to index benchmarking.

2. Avoiding the TOAST penalty. In Postgres, wide attributes are pushed out-of-line into a separate TOAST table (pg_toast). Even when text is slightly smaller, variable-length text bloats tuples and ruins page packing. With a lean 76.8-byte schema, Postgres packs 80 to 100 rows into every single 8KB disk page. That keeps memory buffer cache hits near 100%. If you drop 400-byte text into every row, page density collapses by 80%, forcing the engine to fetch five times more pages off the SSD for every query.

3. Production reality. In high-throughput architectures like Hacker News or Reddit, transactional databases don't store large markdown bodies in their primary relational tables. They store and index the relational routing keys (author, parent comment ID for threading, timestamps, scores, deletion flags), while heavy payloads are stored in object storage (S3/R2) or dedicated document caches. This challenge tests relational indexing and cursor pagination, not full-text search.

The 1 million warmup and the 20 million RAM incident

To insert data quickly, I wrote a Go loader using Jack Christensen’s pgx library. In Go, the standard database/sql driver uses parameterized INSERT INTO ... VALUES (...) queries, which forces PostgreSQL to parse the SQL string, check types, and plan every single batch over the wire.

Instead, pgx implements PostgreSQL’s native raw binary COPY protocol through pgx.CopyFrom. This streams binary tuple streams directly into Postgres table heap pages without SQL parsing overhead. By streaming in chunks of 5,000 rows across a pooled connection, I started with a 1,000,000 row sanity run: 

// 1M rows inserted in 4.2 seconds (~238,000 rows/sec)
// Table size: 76 MB (98 MB with primary key index)
// WAL files: 2 files (32 MB) -> 8 files (128 MB)

Everything felt smooth. So I scaled straight to 20,000,000 rows.

Once the 20 million rows were in, I opened my SQL editor and casually ran: 

SELECT * FROM public.hn_items ORDER BY id DESC;

My RAM usage spiked to 99%. The editor froze, Windows started thrashing page files to swap, and I had to kill the process from Task Manager.

The primary key B-Tree index worked as designed—Postgres scanned backward from the largest id. But asking a database to stream 20 million rows across a socket into client memory with no LIMIT will freeze any machine.

At this point, I realized I did not have anything to visualize what I was doing other than raw SQL commands and terminal outputs. The challenge also specifically asked to build a tiny analytics dashboard. I didn't want to waste my time building a frontend from scratch, so I used an AI assistant to scaffold it. With the right skills file, I got an interface that I genuinely don't hate looking at: live keyset cursor pagination across the heap, index hit badges, and real-time latency charts to profile queries on the fly.

The trap: why adding indexes early murders your loader

At 20M rows, the temptation was to create all secondary indexes immediately (author lookup, parent-child comments, top stories).

Doing that would have been a massive mistake:

If you create secondary indexes at 20 million rows, loading the next 80 million rows forces PostgreSQL to update every single B-Tree on every single insert. Your loader slows to a crawl.

So I kept the table completely unindexed except for the primary key, established an unindexed query baseline, and streamed directly to 50M and then 100M rows first.

On 20M rows, an unindexed scan took 2.4 seconds. On 50M rows, it took 5 to 7 seconds because Postgres had to scan through 4 Gigabytes of raw heap off the SSD.

Streaming 192,000 rows a second

To load the final 50,000,000 rows (from 50M to 100M): 

// Stream 50M rows using raw binary COPY protocol
rowsAffected, err := pool.CopyFrom(
    ctx,
    pgx.Identifier{"hn_items"},
    []string{"parent_id", "created_at", "score", "deleted", "item_type", "author"},
    &BatchRowSource{batchSize: 5000, totalRows: 50_000_000},
)

The results:

The 44 GB WAL mystery

During the 50M row streaming run, my telemetry showed 44 Gigabytes of WAL records generated by PostgreSQL.

On a laptop with 140 GB of free space, generating 44 GB of log files would normally cause panic. But when I checked the WAL directory: 

SELECT count(*) AS files, pg_size_pretty(sum(size)) AS total_size
FROM pg_ls_waldir();
-- Exactly 64 files | 1,024 MB (1.0 GB)

PostgreSQL 18 recycled the WAL segments. As checkpoints completed, Postgres renamed old 16 MB log segments instead of allocating new files on disk. The WAL directory never exceeded its 1 GB ceiling.

The bad index that made queries 5× slower

This was the most surprising lesson of the entire project.

I wanted a query to fetch the top 20 stories sorted by score: 

SELECT id, author, score, created_at
FROM hn_items
WHERE item_type = 'story'
ORDER BY score DESC, created_at DESC
LIMIT 20;

Initially, I created this index: 

CREATE INDEX idx_stories_bad ON hn_items (created_at DESC, score DESC)
WHERE item_type = 'story';

The unindexed sequential scan took 2.1 seconds. With this index, the query time jumped to 11.2 seconds—more than five times slower!

Why? The index was sorted by created_at first. To find stories with the highest score, PostgreSQL had to walk through millions of index pages in timestamp order, filtering out low-scoring stories one by one until it finally found 20 items.

I fixed the column order to match the ORDER BY clause: 

CREATE INDEX idx_stories_top_scoring ON hn_items (score DESC, created_at DESC)
WHERE item_type = 'story';

Query time dropped from 11,200 ms to 0.06 ms. That is an 80,800× speedup over the unindexed baseline.

Why row 99,999,901 takes 5 milliseconds (OFFSET vs Keyset)

Traditional pagination uses OFFSET: 

-- The Slow Way: OFFSET
SELECT * FROM hn_items ORDER BY id ASC LIMIT 20 OFFSET 99999900;
-- Latency: 6,000+ ms (Postgres must read 99.99 million rows and throw them away)

-- The Fast Way: Keyset Cursor
SELECT * FROM hn_items WHERE id > 99999900 ORDER BY id ASC LIMIT 20;
-- Latency: 5.1 ms

With keyset pagination, PostgreSQL traverses the B-Tree directly to the target leaf node in $O(\log N)$ time, reads 20 rows, and stops immediately.

The deletion trap: what actually happens when you delete data?

In the challenge prompt, Chapi threw in a line that caught my eye: "try deletes and backups without nuking performance."

When you're starting out, you assume DELETE is just the opposite of INSERT: you tell the database to delete some rows, and your SSD space comes back.

At 100 million rows, you realize that naive deletes are one of the fastest ways to murder a production database.

What I actually used: the boolean vs deleted_at lesson

In my initial schema, I put in: 

deleted BOOLEAN NOT NULL DEFAULT FALSE

While simple, a bare boolean flag falls short in production:

1. No deletion timestamp. Without a timestamp, you cannot enforce automated data retention policies (like permanently purging records older than 90 days).

2. No grace period. If an account or thread is deleted accidentally, you cannot offer a 30-day recovery window.

While an 8-byte timestamp seems heavier than a 1-byte boolean on paper, deleted_at IS NULL consumes 0 bytes of data payload for active rows (which represent 99% of your data) because PostgreSQL tracks NULLs in a 1-bit null bitmap inside the tuple header.

So adding deleted_at TIMESTAMPTZ DEFAULT NULL gives full audit history without bloating the table heap. In fact, when I ran ALTER TABLE hn_items ADD COLUMN deleted_at TIMESTAMPTZ; on my live 100M row database, it finished in 11 milliseconds flat because PostgreSQL 18 handles NULL defaults as an instant catalog metadata update without touching table pages.

Why you shouldn't hard-delete comments (and what happens to the tree)

If someone deletes a comment on Hacker News or Reddit, what happens if the database runs a hard DELETE FROM hn_items WHERE id = 123;?

Disaster. If that comment had 50 nested replies under it:

- Foreign key constraints throw an error and refuse to delete it.

- Or if cascade delete is enabled, it nukes all 50 innocent replies below it, destroying everyone else's discussion!

- Or all 50 children are left pointing to a parent_id that no longer exists, breaking the frontend tree.

So production platforms keep the row as a tombstone: they set deleted = TRUE (or deleted_at = NOW()) and wipe the author and text to [deleted]. The comment tree stays intact, but personal data is gone.

The storage crisis: why deleting 80M rows leaves disk size unchanged

Here's the real trap. Suppose 80 million rows are deleted, and you're paying AWS or Supabase for storage every month. You check your disk usage...

The database table is STILL 16.7 Gigabytes. You are still paying for 16.7 GB!

Why? Because of PostgreSQL's Multi-Version Concurrency Control (MVCC). When you delete a row, Postgres doesn't erase it from disk. It just marks the row header with an xmax transaction ID so other queries know it's dead. The 8KB disk pages on your SSD stay allocated.

Worse: running a single giant DELETE FROM hn_items WHERE deleted = TRUE; on millions of rows writes 20+ Gigabytes of WAL records, locks table pages, causes replica lag, and freezes client queries.

How production systems actually handle this

1. The Batched Janitor Pattern. Big companies use background reaper daemons. Instead of one massive delete, they delete in small chunks of 5,000 rows with a 50ms sleep in between: 

-- Delete in 5,000-row chunks so queries never stutter
WITH to_delete AS (
    SELECT id FROM hn_items
    WHERE deleted_at < NOW() - INTERVAL '90 days'
    LIMIT 5000
)
DELETE FROM hn_items WHERE id IN (SELECT id FROM to_delete);

Each chunk finishes in ~10 milliseconds, holds locks for microseconds, and lets autovacuum sweep dead tuples in the background without CPU spikes.

2. Partial Indexes. If 80M rows are dead, why keep them in your B-Trees? By indexing only active items: 

CREATE INDEX idx_active_stories ON hn_items (score DESC, created_at DESC)
WHERE deleted = FALSE;

The index size drops from 450 MB to ~90 MB. 80 million dead rows never touch your RAM cache.

3. Reclaiming the SSD space. If you actually want those 16.7 GB back:

- Offline: VACUUM FULL hn_items; rewrites the table into a fresh ~3.3 GB file, but locks out all queries while running.

- Online (what big tech uses): Tools like pg_repack rebuild the table and swap the files with zero downtime.

- Instant: For time-series data, partitioning by month lets you run DROP TABLE partition_2025; and free 100% of the disk space in 50 milliseconds with zero WAL bloat.

What I took away from all of this

Running 100 million rows on a consumer laptop taught me more about database internals than years of small CRUD projects:

1. Hardware is rarely the bottleneck. A consumer laptop can handle 2,600+ queries per second on 100 million records if the access patterns match your B-Tree layouts.

2. Bulk loading requires dropping indexes. Always ingest raw data first, then build indexes concurrently.

3. Order of columns in composite indexes matters. Sorting on the wrong column can turn an index scan into an operation that is 5× slower than a sequential scan.

4. Never use OFFSET for deep pagination. Use keyset cursors (WHERE id > $1) for predictable $O(\log N)$ performance.

5. Lean schemas preserve cache locality. Keeping variable-length text out of the primary OLTP table keeps page density high and buffer cache hits near 100%.

6. The single-machine secret: zero network hop physics. A major reason these latency numbers look so fast—1.03 ms median, 0.06 ms buffer hits, and 2,692 QPS—is that everything ran co-located on the same physical laptop.

In cloud production (like AWS ECS talking across availability zones to RDS Aurora), you instantly inherit an irreducible 0.5 ms to 2.5 ms network round-trip time across VPC virtual switches, packet routing, and NIC interrupts before the database even sees the bytes. Here, Go and PostgreSQL talk over local loopback sharing the same CPU memory bus and PCIe NVMe channel. Network transit latency drops to virtually zero (~0.03 ms). It's an honest engineering reality check: in distributed systems, teams often spend months micro-optimizing SQL to shave 0.2 ms, only to surrender 3 ms to cloud network hops. Single-box colocation shows the true raw ceiling of what PostgreSQL and modern hardware can do when network physics aren't in the way.
